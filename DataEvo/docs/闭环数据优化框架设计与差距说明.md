# DataEvo：Training Dynamics Guided Data Optimization 设计与差距说明

## 1. 当前目标

DataEvo 的目标是实现一个闭环数据优化流程：

```text
数据生成策略
  -> 生成冷启动蒸馏数据
  -> SFT / GRPO 训练
  -> 训练动态与 observation 诊断
  -> Data Controller 更新结构化策略
  -> LLM Prompt Agent 改写下一轮蒸馏 prompt
  -> 下一轮数据生成
```

和 DataObs 的固定冷启动数据不同，DataEvo 会把每一轮训练过程中暴露出的学习信号直接反馈给下一轮数据生成。

## 2. 现在已经实现的部分

### 2.1 不覆盖 DataObs 的独立目录

已经新建 `DataEvo/`，并复制/改造了 DataObs 的核心流程：

- `DataEvo/scripts/experiment_pipeline_vllm.py`
- `DataEvo/scripts/experiment_pipeline.py`
- `DataEvo/lib/data_process/cot_distill_teacher_filter.py`
- `DataEvo/lib/training/sft_dataobs.sh`
- `DataEvo/lib/training/grpo_from_sft.sh`
- `DataEvo/lib/evaluation/eval_vllm.py`
- `DataEvo/tools/grpo_log_metrics.py`

DataObs 原目录没有被修改。

### 2.2 内层 pipeline 对齐 DataObs vLLM 流程

内层每轮仍然走：

```text
distill -> metrics -> sft -> sft_eval -> grpo -> grpo_eval
```

默认外层闭环可以用：

```bash
python DataEvo/scripts/dataevo_pipeline.py \
  --evo-id dataevo_gsm8k \
  --dataset gsm8k \
  --base-model /data/pretrain_models/Qwen3.5-0.8B \
  --teacher-model /data/pretrain_models/Qwen3.5-9B \
  --output-dir /data/hrh/COT/dataevo_experiments \
  --rounds 3 \
  --round-stages distill,metrics,sft,grpo \
  --gpu-ids 0
```

### 2.3 可变蒸馏 prompt 控制

蒸馏阶段已经支持以下动态控制项：

- `--evo-difficulty`: `easy / medium / hard / mixed`
- `--evo-reason-length`: `short / medium / long / mixed`
- `--evo-teacher-type`: `base / instruct / reasoning / specialist / mixed`
- `--evo-prompt-suffix`: 由 controller 或 prompt agent 改写的自由文本 instruction

这些控制项会进入：

```text
DataEvo/lib/data_process/cot_distill_teacher_filter.py
```

并拼接到 dataset-specific answer-format instruction 后面。

### 2.4 Data Controller

位置：

```text
DataEvo/lib/controller.py
```

它负责根据训练动态更新结构化数据生成策略，包括：

- difficulty mix
- reason length mix
- teacher model / teacher type / teacher size
- teacher temperature / top-p
- teacher num samples
- max new tokens
- prompt suffix

已经实现的规则包括：

- 训练早期快速收敛：提高 hard / long reasoning 比例。
- 学习信号弱：提高 learning value，并在 teacher registry 中尝试升级 teacher。
- entropy 持续下降：提高采样多样性、temperature、num samples。
- KL / clip ratio / gradient norm 波动：降低 hard / long / noisy pressure。
- teacher pass rate 低：降低复杂度并尝试更强 teacher。
- empty answer rate 高：降低 temperature 并强制完整答案格式。

### 2.5 LLM Prompt Agent

位置：

```text
DataEvo/lib/prompt_agent.py
```

它现在是一个可插拔 agent：

```text
training dynamics + controller update + observation priors
  -> LLM Prompt Agent
  -> next-round distillation prompt suffix
```

运行方式有三种：

```bash
--prompt-agent-mode heuristic
--prompt-agent-mode llm --prompt-agent-cmd "<your_llm_agent_command>"
--prompt-agent-mode off
```

其中 `--prompt-agent-cmd` 会收到 JSON context 的 stdin，并应输出：

```json
{
  "prompt_suffix": "English distillation instruction...",
  "rationale": "Why this prompt was chosen..."
}
```

如果没有配置外部 LLM command，或者 command 失败，会 fallback 到启发式 prompt agent。这样离线 dry-run 和没有 API key 的环境也能跑完整闭环。

每轮会保存：

```text
feedback/prompt_agent_context_round_000.json
feedback/prompt_agent_round_000.json
```

## 3. 训练动态和 observation 指标保存什么

每轮训练完成后，DataEvo 会生成：

```text
feedback/dynamics_round_000.json
```

当前包含以下信息。

### 3.1 Distill 动态

来自：

```text
rounds/<run>/distill/filtered_sft.summary.json
```

字段包括：

- `num_candidates`
- `num_kept`
- `teacher_pass_rate`
- `kept_rate`
- `prompt_pass_rate`
- `empty_answer_rate`
- `score`
- `answer_length_chars`
- generation setting，包括 difficulty/reason length/teacher type/prompt suffix

### 3.2 SFT 动态

来自：

```text
rounds/<run>/logs/sft.log
```

当前解析：

- `train_loss`
- `val_loss`
- `early_drop_ratio`
- `total_drop_ratio`
- `convergence_index_fraction`
- `first / last / delta / relative_delta / mean / std / min / max / slope`

这些指标用于判断：

- 是否早期快速收敛。
- loss 是否几乎不变。
- 是否存在学习过快或学习不足。

### 3.3 GRPO / RL 动态

来自：

```text
rounds/<run>/logs/grpo.log
```

当前解析：

- `critic/rewards/mean`
- `critic/score/mean`
- `derived/train_accuracy_proxy`
- `derived/val_accuracy_proxy`
- `actor/entropy`
- `actor/kl_loss`
- `actor/ppo_kl`
- `actor/pg_clipfrac`
- `actor/grad_norm`
- `response_length/clip_ratio`

这些指标用于判断：

- RL reward 是否有效提升。
- policy entropy 是否坍塌。
- KL 是否不稳定。
- PPO clip ratio 是否过高。
- gradient norm 是否异常。
- response 是否大量被截断。

### 3.4 Eval 指标

如果本轮跑了 eval，会读取：

```text
eval/sft/generated/responses_labeled.metrics.json
eval/grpo/generated/responses_labeled.metrics.json
```

主要用于记录：

- SFT pass@1 / accuracy
- GRPO pass@1 / accuracy
- GRPO - SFT delta

### 3.5 SC gain / pass@K

如果存在 pass@K 产物，会读取：

```text
passk/passk_metrics.json
passk/passk_metrics.csv
eval/sft/passk/passk_metrics.json
eval/grpo/passk/passk_metrics.json
```

当前会摘要：

- `pass1_pct`
- `passk_pct`
- `pass16_minus_pass1_pp`
- `sc16_pct`
- `sc_gain16_pp`
- `sc_realization_ratio16`

来自 DataObs observation 的结论是：

- `pass@K - pass@1` 衡量采样覆盖面。
- `SC gain` 衡量覆盖面里有多少能被多数投票稳定取出。
- 高 SC gain / pass@K headroom 不等于 RL gain，但说明存在可利用的采样 headroom。
- 如果 GRPO 后 pass@K 或 SC@K 不升，说明 RL 可能只是重排少数轨迹概率，而不是扩大可解覆盖。

### 3.6 Optimization headroom / entropy collapse

如果存在诊断文件，会读取：

```text
diagnostics/optimization_headroom_summary.json
diagnostics/optimization_headroom_joined.csv
optimization_headroom/optimization_headroom_summary.json
optimization_headroom/optimization_headroom_joined.csv
```

DataObs observation 里的有效信号包括：

- `entropy_collapse = Entropy_base - Entropy_SFT`
- `optimization_headroom = Entropy_SFT - Entropy_min`
- final-token / trajectory-token entropy collapse 与 GRPO final-val 呈强负相关。
- headroom 与 GRPO final-val 呈正相关，但 standalone eval 关系还不稳定。

DataEvo 目前把这些作为可选诊断信号输入 prompt agent。

### 3.7 SDS / answer support

如果存在诊断文件，会读取：

```text
diagnostics/sds_summary.json
diagnostics/sds_joined_metrics.csv
sds/sds_summary.json
sds/sds_joined_metrics.csv
```

DataObs observation 中更有用的是：

- `answer_sds`
- `sft_answer_unseen_frac`
- `useful_off_support_frac`
- `harmful_regression_frac`

结论是：

- exact trajectory SDS 在当前采样数下几乎饱和，不适合当主信号。
- answer-level SDS 需要拆成有用 off-support 和 harmful regression。
- prompt agent 会倾向保留有用 off-support，同时压低 harmful regression。

### 3.8 Template / recovery / turning point

如果存在诊断文件，会读取：

```text
diagnostics/source_template_metrics.csv
diagnostics/template_summary.json
diagnostics/model_summary.csv
diagnostics/recovery_turning_point_summary.json
```

有效 observation 包括：

- distinct-n
- opening concentration
- cluster entropy
- trajectory entropy
- recovery pattern frequency
- turning point frequency
- average turning point position

使用方式：

- 模板化强时，让 prompt agent 改写为多样化 reasoning style。
- recovery/turning point 高时，强调真实自检，不鼓励模板化 `wait / let me check`。
- medium difficulty 是 recovery 最有信息量的区间。

## 4. 和原始需求逐项比对

### 4.1 已经满足

| 原始需求 | 当前状态 |
|---|---|
| 新建 DataEvo，不覆盖原代码 | 已完成 |
| pipeline 对齐 `DataObs/scripts/experiment_pipeline_vllm.py` | 已完成，复制并改为 DataEvo 路径 |
| 数据生成 -> 模型训练 -> 动态分析 -> 策略更新闭环 | 已完成外层 orchestrator |
| difficulty / reason length / teacher size / teacher type / prompt 可变 | 已实现结构化策略和 distill prompt suffix |
| 训练动态包括 loss、learning speed、KL、clip ratio、entropy、grad norm、convergence speed | 已解析主要日志指标 |
| 不预测抽象数据质量分，而是直接用训练信号反馈 | Data Controller 按规则直接使用 dynamics |
| 下一轮根据反馈调整蒸馏 setting | 已实现 |
| 记录每轮策略、反馈、命令和动态 | 已实现 |
| 加入 LLM agent 改写蒸馏 prompt | 已实现可插拔 `PromptAgent`，支持外部 LLM command |
| 动态信息包含 SC gain 等 DataObs observation 里的有效指标 | 已加入 pass@K/SC、SDS、headroom、template、recovery 的可选读取入口 |

### 4.2 还没有完全满足

| 缺口 | 原因 | 下一步 |
|---|---|---|
| LLM agent 目前不是内置 OpenAI/本地模型 API 调用 | 为避免绑定具体 API key、服务地址和网络环境，先做成 `--prompt-agent-cmd` 插件 | 接一个具体 LLM backend，例如本地 vLLM server、OpenAI API、或你已有 agent 脚本 |
| SC gain/pass@K 不是每轮默认计算 | 当前内层 eval 默认是 pass@1，pass@K 需要多采样 eval 和 `plot_passk.py` 产物 | 给 DataEvo 增加 `passk_eval` stage，自动对 SFT/GRPO checkpoint 做 K=16 采样 |
| SDS/headroom/template/recovery 不是每轮默认计算 | 这些 observation 原本是离线分析脚本，成本较高，有些需要多采样或模型 entropy 计算 | 把 DataObs 对应工具迁移成 DataEvo diagnostic stages，并支持 smoke / sampled 版本 |
| 训练动态里的 perplexity 还不是 train-time PPL 曲线 | DataObs PPL 是数据侧可选指标，不是训练 step PPL | 从 SFT eval loss 或单独 PPL diagnostic 中补 step-level / heldout PPL |
| teacher size/type 的自动选择比较简单 | 当前只按 registry 顺序尝试升级 teacher | 增加 teacher budget、GPU 可用性、teacher family、task specialist routing |
| difficulty mix 目前转成 dominant profile | 真实混合比例还没有用于按比例采样不同 prompt 模板 | 增加多模板分桶生成，让同一轮内按 mix 比例生成 easy/medium/hard 数据 |
| prompt agent 现在只改 suffix，不替换完整 dataset-specific template | 为了避免破坏 GSM8K/MATH/代码等 final answer 格式 | 增加安全的 `distill_template_patch`，只允许改 reasoning instruction，不允许改 final format |
| RL rollout 内部 recovery/turning point 没有在线统计 | 当前只解析 GRPO 日志，不解析 rollout 文本 | 在 GRPO 训练保存 rollout samples，并接 recovery/turning-point parser |
| controller 规则阈值还未基于新实验校准 | 当前阈值来自 observation 直觉和保守默认 | 跑多轮 DataEvo 后，用 history 重新校准阈值 |

## 5. 建议下一步实现顺序

### Step 1：接入真实 LLM Prompt Agent

实现一个命令，例如：

```bash
python my_llm_prompt_agent.py
```

要求：

- stdin 读取 JSON context。
- stdout 输出 JSON：

```json
{
  "prompt_suffix": "Generate reasoning with ...",
  "rationale": "Because entropy collapsed and SC realization was low ..."
}
```

然后运行：

```bash
python DataEvo/scripts/dataevo_pipeline.py \
  ... \
  --prompt-agent-mode llm \
  --prompt-agent-cmd "python my_llm_prompt_agent.py"
```

### Step 2：把 pass@K/SC gain 变成正式 stage

新增：

```text
passk_sft_eval
passk_grpo_eval
```

每轮生成：

```text
eval/sft/passk/passk_metrics.json
eval/grpo/passk/passk_metrics.json
```

这样 SC gain、pass@K headroom 才能成为每轮稳定反馈，而不是“如果文件存在就读”。

### Step 3：把 observation diagnostics 模块化

建议新增：

```text
DataEvo/lib/diagnostics/
  passk_sc.py
  sds.py
  entropy_headroom.py
  template_collapse.py
  recovery_turning_point.py
```

每个 diagnostic 都支持：

- quick sampled mode
- full mode
- JSON summary output
- controller/prompt agent 可读的统一 schema

### Step 4：让 difficulty mix 真正控制同轮数据组成

当前一轮只有 dominant profile，比如 `hard` 或 `mixed`。更理想的是：

```text
hard: 40%
medium: 45%
easy: 15%
```

然后 distill 阶段按比例生成不同 prompt profile 的样本，并在输出 parquet 里保存：

```text
evo_difficulty_profile
evo_reason_length_profile
evo_prompt_agent_version
```

这样后续可以分析哪类生成策略真正有效。

### Step 5：把 RL rollout 文本纳入动态分析

目前 GRPO 动态偏数值日志。要更贴近你原始想法，需要保存训练期间 rollout response，并分析：

- rollout answer diversity
- rollout entropy / template collapse
- rollout recovery / turning point
- correct unseen answer
- harmful regression

这会让反馈不只依赖 reward/KL/entropy，也能看到推理行为本身如何演化。
